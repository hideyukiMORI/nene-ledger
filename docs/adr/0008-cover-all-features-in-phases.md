# ADR 0008 — 機能は全部カバーする。一覧を正本にしてフェーズで覆い、7 つの論点をこう決める

- 状態: 受理
- 日付: 2026-10-22
- Issue: #4
- 影響する規則: ARC-001 / ARC-009 / ARC-013 / QLT-013 / QLT-014

## 文脈

Issue #3 で、文献・競合 17 製品・速さの比較・利用者の要望とペルソナ討議から、CSV / TSV エディターに要る機能を 185 項目に洗い出した（[docs/research/](../research/2026-10-22-feature-catalog.md)）。
施主は「フェーズは別として全部カバーしたい」と決め、討議で残った 7 つの論点について AI の推しをそのまま採った（2026-10-22）。

## 決定

**機能は全部カバーする。細目の正本を `docs/FEATURES.md` に置き、各機能にフェーズ（1 / 2 / 3）と状態を持たせる。SPECIFICATION の FR は大きな約束のまま残し、細目は番号で引く。**

1. **一覧の置き方**: FR を 185 本に増やさない。FEATURES.md の番号（`OPEN-01` など）は変えず、各機能はちょうど 1 つの FR に属する。フェーズ 1 は Must（約束の芯）、2 は Should、3 は Could。状態の `確認済み` はテストか実測の記録を名指しできるものだけ（QLT-013 / QLT-014）
2. **手順（レシピ）の形式**: 独自の、版付きの、人が読めるテキストにする（ARC-009）。方言と列の規則の部分だけは Frictionless / CSVW の語彙に寄せる。OpenRefine の操作履歴の取り込みはフェーズ 3（AUTO-08）
3. **SQL**: 入れる（フェーズ 3・AUTO-06）。範囲は読み取り専用（SELECT・WHERE・GROUP BY・ORDER BY・JOIN）で、結果は表の見えか新しいファイル。**GUI の操作と同じ自前のエンジンへの入口として作り、SQL 専用のエンジンを持たない**（ARC-001・ADR 0007）。UPDATE / DELETE は入れない（書き換えの経路は編集と保存の 1 本・ADR 0005）
4. **取り込み先のプリセット**（楽天・弥生・Shopify など）: 配る（フェーズ 2・VALD-05）。ただし**コードに焼き込まず、規則ファイルとして同梱する**。ファイルに確かめた日付と出典を持たせ、古くなったことが分かるようにする
5. **xlsx / Parquet**: **xlsx の書き出しをフェーズ 2 に入れる**（SAVE-08）。全セルを文字列として保存し、相手の Excel で先頭の 0 も日付も壊れない。xlsx の読み込み（値と表示の書式のどちらを取るかを選ぶ）と Parquet はフェーズ 3（SAVE-09 / SAVE-10）。依存は導入の Issue で ADR（ARC-013）
6. **和暦**: 入れる（フェーズ 2・XFRM-08）。明示の変換だけで、自動では変えない。元号の表はデータファイルで持ち、改元は表を足すだけ
7. **印刷と PDF**: フェーズ 3（PRNT-01）。OS の印刷の仕組みに乗る（Windows は Direct2D の印刷・「Microsoft Print to PDF」、Linux は cairo の PDF）。日本語のフォントの PDF への埋め込みを自前で書かない
8. **やらないこと**: データを外に送る機能（クラウド・AI・テレメトリ・Web / API からの取り込み）と、スクリプト言語の組み込み（AUTO-07）。繰り返しの要望には手順（AUTO-01）・SQL（AUTO-06）・コマンドライン（AUTO-05）で応える

## 強制

- **planned**: FEATURES.md の整合（番号の重複・FR の実在・`確認済み` に記録の名指しがあること）を機械で見ることは、CNF-009（文書整合）の拡張として Issue #2 以降で検討する
- **不能**: 「全部カバーした」と言ってよいかの判断。状態の列の正直さはレビューでしか担保できない

## 結果

得られるもの:

- 「何を作るか」が 189 項目で一覧でき、どれがいまどこまでかを 1 か所で数えられる
- 大きな約束（FR）と細目（FEATURES）が分かれ、約束が細目に埋もれない
- 競合が持たない機能（一覧の「無」）が差別化として見える

失うもの・残る穴（**正直に**）:

- 🔴 **作る量が非常に多い。** フェーズ 3 まで全部で 189 項目。フェーズ 1 だけで 86 項目ある
- 🔴 xlsx の書き出し・Parquet・正規表現・SQL は、依存を入れるか自前で書くかで重さが大きく変わる。各導入の Issue で ADR を立てる
- 状態の列は人が書く。機械の検査が入るまでは、`確認済み` の正しさはレビューに頼る
- 優先度は討議（AI が演じたペルソナ）による提案を施主が採ったもので、実際の利用者で確かめていない

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 機能を全部 FR にする（FR-001〜185） | 約束と細目が混ざり、SPECIFICATION が読めなくなる |
| 一覧を調査の記録のままにする | 規範でないものは「作ったか」を数えられない |
| 手順の形式を OpenRefine の JSON にする | OpenRefine の内部に結び付いた形で、列の見方・バイト列を保つ保存・方言の変更などを表せない |
| SQL 専用のエンジン（または組み込みの DB）を持つ | GUI と SQL で並べ替えや比較の結果が食い違う。第 2 の経路（ARC-001）・ADR 0007 |
| プリセットをコードに焼き込む | 業者の形式は予告なく変わる。直すたびに本体の改修が要る |
| xlsx を一切やらない | 要望 1 位（勝手に変えない）を Excel の利用者まで届ける一番の手段を捨てることになる |
| PDF を自前で書く | 日本語のフォントの埋め込みが重い。要望も弱い |
| スクリプト言語を組み込む | 依存が非常に大きい。繰り返しは手順・SQL・コマンドラインで足りる |

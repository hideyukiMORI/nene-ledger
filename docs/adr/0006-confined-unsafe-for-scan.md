# ADR 0006 — 原本の写像と SIMD の探索のために、`scan` の 1 クレートにだけ `unsafe` を許す

- 状態: 受理
- 日付: 2026-10-22
- Issue: #1
- 影響する規則: RS-010 / RS-005 / ARC-005 / ARC-007 / QLT-008 / CNF-012 / CNF-014 / CNF-015 / FR-004

## 文脈

NeNeDocket は `unsafe` を Windows の 2 クレートにだけ許した（NeNeDocket ADR 0002）。
NeNe Ledger の心臓部は、巨大なファイルを速く読むことである（FR-004）。そこには `unsafe` を要する手段が 2 つある。

- **写像（mmap）**: ファイルを記憶に直接割り当てる。`memmap2` の `Mmap::map` も OS の直呼びも `unsafe` である。ほかのプロセスがファイルを変えると、読んでいる中身が変わる
- **SIMD**: 区切り文字・改行・引用符を一度に探す。`std::arch` の命令は `unsafe` である（引用符の内外の判定は simdjson と同じ carry-less multiply の手法）

施主は「`unsafe` を許すクレートの ADR を最初に 1 本立てる」ことに同意した（2026-10-22）。

## 決定

**`crates/scan` の 1 クレートにだけ、Windows の 2 クレートと同じ形で `unsafe` を許す。規則の正本は core に置き、scan はそれを速く実行するだけにする。**

1. `scan` の lint の表は workspace の写しで、`unsafe_code = "deny"` だけが違う。CNF-014 が同じであることを見る
2. `unsafe` を要する小さな関数ごとに `#[expect(unsafe_code, reason = "RS-010: …")]` と `// SAFETY:` を置く（`undocumented_unsafe_blocks`）
3. **core に参照実装を置く。** セルの切り出し（区切り・引用符・改行）の素朴で正しい純関数を core に置き、scan の速い経路は、同じ入力に対して同じ行の境界とセルを出すことをテストで固定する（QLT-008 の 1）。テストには乱数で作った入力（引用符・改行・区切りの組み合わせ）を含める。乱数の種は固定する（ARC-007）
4. **切り方に依らない。** 並列に読むときの区切りの位置（引用符の中か外か分からない所）は、両方の場合を仮に計算して後で突き合わせる。スレッドの数と区切りの位置を変えても結果は同じ（QLT-008 の 2）
5. **SIMD は実行時に確かめる。** CPU の機能を確かめてから使い、無ければ素朴な経路へ落とす。どちらの経路も 3 のテストを通る
6. **写像は、危険への備えを決めてから入れる。** 写像を製品の経路に入れるのは、次を実装の Issue で測って決めた後である。それまでの既定は、安全な読み出し（`read` でバッファに読む）
   - Linux: 写像を読んでいる間に他のプロセスがファイルを縮めると、読んだ瞬間にプロセスが落ちる（SIGBUS）。シグナルを捕まえるか、写像を使わないか、危険を明記して受け入れるか
   - Windows: 写像の間は他のプロセスがファイルを縮められない（`SetEndOfFile` が失敗する）。そのぶん、Excel などの保存を妨げうる。共有の指定（`FILE_SHARE_*`）をどうするか
   - 写像と読み出しの速さの差（ページキャッシュに載っているとき・載っていないとき・ネットワーク共有の上）
7. scan は書き込みの API を使わない（CNF-015・ADR 0005）
8. 依存（`memchr` / `memmap2` 等）を使うか、`std::arch` と OS の直呼びで書くかは、導入の Issue で ADR を立てて決める。**依存に任せれば自前の `unsafe` が減る**ことも比べる材料にする

## 強制

- **planned**: CNF-014（scan を含む 3 クレートの lint の表）・CNF-015（書き込みの API）・`undocumented_unsafe_blocks`。scan を作る Issue で実ファイルの発火を記録する
- **不能**: `unsafe` の中の正しさそのもの。参照実装との一致のテスト（QLT-008）と、`// SAFETY:` の注釈のレビューでしか見られない

## 結果

得られるもの:

- 速さの源（写像・SIMD・並列）を、1 つのクレートに閉じて持てる
- 速い経路の正しさの基準（core の参照実装）が 1 つに決まる（ARC-001）
- 写像を入れない判断もできる。決定の 6 により、危険を測る前に製品の経路に入らない

失うもの・残る穴（**正直に**）:

- 🔴 **`unsafe` を許す区画が 2 から 3 になる。** 区画の中で規則（`unwrap` の禁止など）は効くが、メモリの安全はコンパイラではなく注釈とテストが支える
- 🔴 **写像の SIGBUS は、Rust の安全性の外にある。** 捕まえる実装も `unsafe` で、移植性が低い
- `indexing_slicing` の禁止は、バイト列の走査で書き味の摩擦になる。`get` と反復子で書いて測り、足りなければ ADR
- 参照実装との一致のテストは、テストした入力についてしか保証しない

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| `unsafe` を一切書かず、依存に任せる | 自前の `unsafe` は減るが、依存の中の `unsafe` は残る。SIMD による引用符の判定のように、この製品に合わせた形は依存に無いことがある。決定の 8 で依存に任せる道も残す |
| 中核（core）に `unsafe` を許す | 中核は `#![no_std]` で OS を知らない（ARC-003）。速さの都合を中核に持ち込まない |
| `unsafe` を許すクレートを機能ごとに増やす（写像用・SIMD 用） | 区画が増えるほど見る所が増える。読み取りの速さという 1 つの責務に 1 つの区画 |
| 写像を最初から既定にする | SIGBUS とロックの問題を測る前に入れることになる。決定の 6 |

# ADR 0019 — 切り出しの規則に「文字の単位」を入れ、区切り・引用符・改行は文字の頭でだけ見分ける

- 状態: 受理
- 日付: 2026-10-26
- Issue: #35（Shift_JIS の 2 バイト目）・#36（UTF-16）
- 影響する規則: ARC-001 / ARC-003 / RS-001 / RS-002 / QLT-008 / FR-002 / FR-003 / FR-023。OPEN-09・JP-01・ADR 0005 / 0006 / 0015 / 0017

## 文脈

規則の正本（core の `scanning`）と、それと同じ結果を出す scan の状態機械（`RecordStarts`）は、1 バイトずつ見て、区切り・引用符・改行・エスケープのバイトを見分ける。これが正しいのは、どのバイトも 1 つの文字（か文字の一部で ASCII と重ならないもの）であるときだけである。今はそうでない組を `TextFormat::new` が断っている（Issue #18）。

- **Shift_JIS（CP932）**: 2 バイトの文字の 2 バイト目は 0x40〜0x7E・0x80〜0xFC で、ASCII の `@`〜`~` と重なる。「表」は `95 5C` で、2 バイト目が `\` である。区切り・引用符・エスケープがこの範囲（`|` や `\` など）なら漢字の途中で誤って切る。`,`・`\t`・`"`・改行は 0x40 より小さいので、今も正しく切れている。断るのは `FormatFailure::ShiftJisTrailByte`
- **UTF-16**: すべての文字が 2 バイト（か 4 バイト）の単位で、`,` は `2C 00`（LE）。1 バイトずつでは切れない。断るのは `FormatFailure::NotAsciiCompatible`
- EUC-JP の 2 バイト目は 0xA1〜0xFE で ASCII と重ならないので、今のままで正しい

日本の経理の現場では Shift_JIS のファイルが多く、Excel の「Unicode テキスト」は UTF-16LE のタブ区切りである。開けないファイルを残したくない（施主 2026-10-26・文字コードの残りを進める）。

## 決定

**切り出しの規則の正本は、方言が持つ閉じた集合「文字の単位」（`TextUnits`）に従って文字ごとに進み、区切り・引用符・改行・エスケープは文字の頭でだけ見分ける。位置は今までどおりバイトの位置で持つ。**

1. **文字の単位**: `TextUnits { SingleByte, ShiftJis, Utf16Le, Utf16Be }`。`TextFormat::new` が文字コードから決めて方言に入れる（UTF-8・EUC-JP・Windows-1252 は `SingleByte`。利用者は直接選ばない）。判別（`Detection`）も、推し量った文字コードの単位で候補を試す
2. **Shift_JIS**: 1 バイト目（0x81〜0x9F・0xE0〜0xFC）の次のバイトが 2 バイト目として正しい（0x40〜0x7E・0x80〜0xFC）ときだけ、2 バイトを 1 つの文字として飛ばす。正しくなければ 1 バイトの文字として読む（壊れたファイルで改行や区切りを飲み込まない）。エスケープ（`\`）が逃がすのも 1 文字
3. **UTF-16**: 2 バイトの単位で進み、単位の値を ASCII の区切り・引用符・改行と比べる（サロゲートの半分は ASCII と重ならない）。BOM の後ろから切る（Issue #18 のとおり）。奇数の長さの最後の 1 バイトは入力の終わりとみなす
4. **位置**: セル・レコード・索引の目印・範囲の取り出しは、どれもバイトの位置のまま（ADR 0017）。セルの値は、文字の単位で引用符とエスケープを外してから、`encoding_rs` で復号する（ADR 0015）
5. **速い経路**: scan の状態機械は、文字の途中の状態（2 バイト目を待つ・単位の片方を持つ）を塊の境目を越えて持ち越す。正本と同じ区間と境目を出すことを、乱数の入力 × 方言 × 文字の単位 × 塊の大きさのテストで固定する（ADR 0006）
6. **保存**: 変わらない。触っていない行はバイト列のまま書き戻す（ADR 0005）

## 強制

- **active（実装後）**: 正本と scan の一致のテスト（文字の単位ごと）。Shift_JIS の 2 バイト目が区切り・引用符・エスケープと重なるファイルの切り出しと値のテスト。壊れた並び（1 バイト目の次が改行）のテスト
- **active（Issue #36）**: UTF-16 の正本と scan の一致・UTF-8 と同じ表になることのテスト
- **不能**: 「Shift_JIS と推し量ったファイルが本当に Shift_JIS か」は判別（ADR 0015）の確からしさに依る。迷えば候補を示す（FR-023）

## 結果

- 得るもの: Shift_JIS で `|`・`\` を区切りや引用符に使うファイルと、UTF-16 のファイルを、原本を書き換えずに開ける。位置はバイトのままなので、索引・範囲の取り出し・保存の仕組みは変わらない
- 失うもの: 切り出しの各所で文字の幅を見る分だけ遅くなる（`SingleByte` は今と同じ道を通るようにして、差を測ってから QLT-014 に記録する）
- 残る穴: Shift_JIS の判別を誤ったファイル（実は別の 2 バイトの文字コード）では、文字の頭の見分けがずれる。GBK・Big5 などは扱わない（判別の候補に無い）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 開くときに UTF-8 へ変換した写しを作って切る | 巨大なファイルで写しの分の時間と場所が要る。位置が写しのバイトになり、索引と保存（原本のバイト列を写す）と食い違う |
| Shift_JIS の 2 バイト目と重なる方言は断り続ける | `|` 区切りの Shift_JIS は業務の連携ファイルで実在する。開けないファイルを残す |
| 文字の単位を方言ではなく、切り出しの関数の引数にする | 切り出し・値・判別・scan の呼び出しすべての形が変わる。方言は今もすべての所に渡っているので、そこに載せるのが 1 つの経路で済む |

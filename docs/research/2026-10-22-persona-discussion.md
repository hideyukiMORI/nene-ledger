## ターン 1 — いちばん困っていること・絶対に要るもの

**分析**: Excel が黙って 1,048,576 行で切ること。気付かずに一部で集計した経験がある〔要望 1〕。要るのは、全部の行が入ることと、列の見出しからチェックボックスで絞れるフィルター。それと値の分布がすぐ見たい。

**ETL**: 数億行を「見る」だけなら CLI でいい。困るのは**直して戻す**こと。Modern CSV は大きいと読み取り専用になる〔競合・Modern〕。数百万行の削除で固まるのも困る。進み具合と中止が欲しい〔要望・ETL〕。そして保存したら引用の付け方まで元のまま、が絶対条件。

**EC**: JAN の先頭の 0 と指数表記。15 桁を超えた桁は 0 になって戻せない〔要望・EC〕。楽天は列が 1 つずれると全行エラーで、ログは「項目数が一致しません」だけ。どの行の何列目かを教えて欲しい。

**経理**: 弥生は Shift_JIS・CRLF・決まった項目数でしか取り込めない。改行が CR だとエラーの理由も出ない〔要望・経理〕。今のファイルの文字コード・改行・列数が**画面にいつも見えている**ことが要る。銀行の明細は日付も負の数の書き方もばらばら。

**研究**: SEPT1 が 9 月 1 日になる問題で、HGNC が遺伝子名を変えた〔文献・Bruford 2020〕。型を推し量らないのは当たり前。あとは数百 MB の行列を転置したい。

**翻訳**: セルの中の改行。54 列のうち 33 列目の改行で以降が全部ずれた〔要望・翻訳〕。改行と見えない文字（ノーブレークスペース）が見えること、戻ってきた訳をキーで元と突き合わせられること。

**CRM**: 重複と、メールアドレスの空白と大文字小文字。HubSpot は大文字小文字の違いで黙って空欄にする〔要望・CRM〕。取り込み先の項目名への列の割り当てが欲しい。

**ログ**: ファイルが伸び続ける。追記を追いかけて、正規表現で絞って、時刻ごとの件数が見たい〔要望・ログ〕。

**GIS**: 地域設定で `-58.030128` が -58,030,128 になる。座標は文字列のまま。WKT のような巨大なセルを開いても固まらないこと。

**公開**: 「1 セル 1 データ」「機種依存文字を使わない」「UTF-8（BOM 付き）」を守って作る〔要望・公開〕。公開する前に検査したい。

**QA**: 種を固定したダミーデータの生成。それと、境界値（空・巨大・特殊文字）を混ぜた行を手で足したい。

**形式**: 規格としては RFC 4180 しかなく、それも Informational〔文献・RFC 4180〕。現実は引用の流派・改行の混在・列数の不ぞろい・コメント行・複数の表。**寛容に読み、厳密に書く。そして読んで何も変えずに保存したら、バイト単位で同じ**。これが土台。

**速さ**: GUI のエディターの数値は、ほぼメーカーの自己申告で、同じ機械での第三者の比較が無い〔速さの比較・結論〕。最初の画面までと全体の読み込みの終わりを分けて測ること、そして**保存の往復**を誰も測っていない〔速さの比較・空白 3〕。そこで勝てる。

**UX**: 研究では、直接の操作から変換を提案してプレビューし、手順を履歴として残すと、速く監査できる〔文献・Wrangler〕。表の UI は 500 ms を超えると対話でなくなる〔文献・Rahman 2020〕。

**安全**: CSV インジェクション。セルの先頭の `=` `+` `-` `@` が Excel で数式になる〔文献・OWASP〕。エディター自身は絶対に評価しないこと。病的な引用でパーサーが 2 乗の計算量になる例もある。

**文字**: Shift_JIS と CP932 は違う。`①` `㈱` `髙` は CP932 の拡張で、波ダッシュは変換表で U+301C と U+FF5E に割れる〔落とし穴 13・14〕。保存の前に「この文字は表せない・往復で変わる」を出すべき。

**A11y**: 競合のどれもアクセシビリティを書いていない〔競合・空白〕。自前で描くなら、スクリーンリーダーは何も読めない。最低でもキーボードだけで全部できること、拡大と高コントラスト。

## ターン 2 — ぶつかる論点を詰める

### 論点 A: 「型を推し量らない」と「数や日付で並べたい・統計が欲しい」

**分析**: 数の列を文字列で並べられると 10 が 2 より前に来る。統計も数として計算したい。

**研究**: でも自動で型を決めたら SEPT1 の二の舞いだ。

**形式**: 2 つを分ければいい。**値は常に文字列。「この列を数として見る」は利用者が選ぶ見方**で、比較・統計・書式だけに効き、保存には効かない。CSVW も「文字列の値」と「型付きの値」を分けている〔文献・CSVW〕。

**UX**: 選ばせるだけだと手間が増える。列ごとに「数として読める率 98%」を出し、ワンクリックで見方を切り替えられるように**提案**する。自動で適用はしない。数として読めない 2% は一覧で見せる。

**速さ**: 見方は列の比較関数の切り替えなので、索引の作り直しは要らない。数として読んだ値は列ごとに一度だけ計算して持てる。

→ **合意: 値は文字列・見方は列ごとに明示・提案はするが自動で適用しない。読めない値の件数と一覧を出す。**

### 論点 B: 巨大なファイルを「編集して保存」するか

**ETL**: 読み取り専用なら CLI で足りる。編集して保存できるのが価値。

**速さ**: 保存は全体の書き直しになる（ADR 0005）。10 GB なら書くだけで数十秒、置き換えに同じだけの空きが要る。

**経理**: 経理のファイルは小さい。でも 1 行直して保存に何十秒もかかるなら困る。

**形式**: 触っていない区間は元のバイト列をそのまま写すだけなので、書き出しは解析なしの写しになる。ディスクの速さが上限。

**UX**: 書き出しの進み具合・残り時間・空きの事前の確認・中止。保存中も画面は止めない。

→ **合意: 巨大でも編集と保存ができることを差別化にする。保存は裏で、進み具合と中止付き、空きを事前に確かめる。保存の往復の時間を測って公表する。**

### 論点 C: SQL か、GUI の操作か

**ETL**: SQL が欲しい。SmoothCSV にもある〔競合・SmoothCSV〕。

**分析**: 私は SQL を書かない。でも同じ前処理を毎月やる。

**UX**: 両方の要望の芯は「**同じ処理を繰り返したい・何をしたか残したい**」。GUI の操作をそのまま手順（レシピ）として記録し、名前を付けて保存・別のファイルに再生・中身を読める形で書き出せるのが先。OpenRefine の操作履歴の JSON がそれ〔要望・パワーツール〕。

**速さ**: SQL は問い合わせの最適化まで自前で作ると大物になる（ADR 0007）。絞り込み・並べ替え・集計・結合の GUI が先で、SQL はその上の別の入口として後から。

→ **合意: 手順の記録と再生を初版の柱に。SQL は後の版（Could）。**

### 論点 D: 取り込み先ごとのプリセット（楽天・弥生・Shopify）

**EC / 経理 / CRM**: 楽天用・弥生用のボタンがあれば一番楽。

**形式**: 業者の形式は勝手に変わる。製品に焼き込むと古くなる。

**UX**: 汎用の「**書式の規則**」（方言・列の順と名前・必須・型・長さ（全角を 2 と数えるバイト数も）・選択肢・一意）を作り、検証と書き出しに使う。規則はファイルとして保存・共有できる。プリセットは規則ファイルの例として配る。

**公開**: オープンデータの作成ルールも規則で書ける。Frictionless の Table Schema に寄せれば外とも交換できる〔文献・Frictionless〕。

→ **合意: 規則（スキーマ）による検証と書き出しを Should。業者別のプリセットは規則ファイルとして配り、製品のコードに焼き込まない。**

### 論点 E: Excel に渡すとき

**EC**: 最後は誰かが Excel で開く。そこで壊れる。

**安全**: Excel 向けの無害化（`'` を付ける）はデータを変える。既定でやってはいけない〔文献・OWASP〕。

**研究**: 相手の Excel の設定次第で先頭の 0 も消える〔文献・Microsoft の自動変換〕。

→ **合意: 既定の保存は何も変えない。別に「Excel で開くと壊れる値」の警告（先頭の 0・15 桁超・E 表記・日付に見える値・数式に見える値）と、明示の「Excel 向けに書き出す」（BOM・全セルの引用・無害化の選択）を用意する。**

### 論点 F: 文字コードの往復

**経理**: 社内は Shift_JIS、国の提出は UTF-8。同じ表を両方で出す。

**文字**: 保存の前に「表せない文字の一覧（行・列）」と「往復で変わる文字（波ダッシュ等）」を出し、置換の候補を出す。CP932 と JIS の Shift_JIS を区別して選ばせる。

**翻訳**: 文字化けしたファイルを開いたときに、別の文字コードで開き直しが一瞬でできること。

→ **合意: 文字コードの判別・開き直し・保存の前の検査を Must。正規化（NFKC・全角半角）は明示の変換。**

### 論点 G: 壊れたファイル・変なファイル

**ETL**: 引用が閉じていない行で全体が 1 セルになるのは最悪。

**形式**: 壊れた行は「壊れた行」として、元のバイト列のまま隔離して見せる。DuckDB の `store_rejects` と同じ発想〔要望・パワーツール〕。複数の表が 1 ファイルにある場合（最大 226 表の実例）も、空行のブロックを検出して教える〔文献・Pollock〕。

**安全**: セルの長さと判別に読む量に上限を置く。病的な入力で固まらない。

**速さ**: 読み込みのテストに Pollock の 2,290 ファイルをそのまま使える。正しく読めるかも速さと一緒に測る。

→ **合意: 壊れた行の隔離・列数の異常の一覧・ジャンプを Must。複数の表の検出は Should。**

### 論点 H: 差分

**翻訳 / EC / QA**: 2 つの版をキー列で突き合わせたい。テキストの diff では役に立たない〔要望・国内の差分〕。

**速さ**: キー列の索引を両方に作れば、巨大でも突き合わせられる。

→ **合意: キー列での差分（追加・削除・変更をセル単位）を Should。マージは Could。**

### 論点 I: アクセシビリティ

**A11y**: 最低ラインは、キーボードだけで全操作・フォーカスが見える・拡大・高コントラスト・OS の文字の大きさに従う。スクリーンリーダーは Windows の UI Automation で表を出せば、セルを読ませられる。

**UX**: 表だけでも UI Automation の Grid パターンに載せれば価値が大きい。競合のどこも書いていない〔競合・空白〕。

→ **合意: キーボード完結・高コントラスト・拡大は Must。UI Automation は Should（ADR 0002 の「残る穴」を埋める Issue を立てる）。**

### 論点 J: 外にデータを出す機能

**分析**: AI に列の意味を当てさせたい。クラウドで共有したい。

**安全 / 経理**: 経理や顧客のデータを外に送る機能は、それだけで社内で使えなくなる。

→ **合意: データを外に送る機能（クラウド・AI・テレメトリ）は入れない（SPECIFICATION 第 3 節）。Web から取り込む・API で値を補う（qsv の fetch）も入れない。**

### 論点 K: ログの追従・巨大なセル・地図

**ログ**: 追記の追従は要る。

**速さ**: 索引を末尾から伸ばすだけなので、作りとしては素直。ただし ADR 0005 の「外部の変更」の検出と同じ所を通る。

**GIS**: 巨大なセル（WKT・JSON）は詳細ペインで見たい。地図は贅沢。

→ **合意: 追記の追従は Should。セルの詳細ペイン（折り返し・JSON の整形表示）は Must。地図は Won't（初版）。**

## ターン 3 — まとめ

**UX**: 柱を 3 つに絞ると、(1) **何も壊さない**（読み・表示・保存・Excel への受け渡し）、(2) **巨大でも止まらない**（最初の画面・裏の処理・保存の往復）、(3) **繰り返せる・確かめられる**（手順の記録・規則による検証・差分）。

**形式**: (1) の中身は、往復のバイト一致・方言の全項目の保持・壊れた行の隔離・文字コードの保存前の検査。どれも Must。

**速さ**: (2) は、測り方を最初に決めて公表すること。最初の画面・全体の索引・並べ替え・絞り込み・集計・**保存の往復**・メモリの倍率・正しく読めた率。比較相手は EmEditor・Modern CSV・SmoothCSV・DuckDB・qsv〔速さの比較〕。

**ETL**: (3) の手順は、GUI で 1 回やったことを次のファイルに再生できればまず十分。

**EC / 経理 / CRM**: 規則による検証で「どの行の何列目が、なぜ駄目か」が出れば、取り込みの事故の大半は防げる。

**文字 / 経理**: 日本の要望（CP932・表せない文字・全角半角・バイト数・和暦・全項目の引用）は、海外製が弱い所で差別化になる。

**安全**: 数式に見えるセルの強調と、Excel 向けの書き出しでの選べる無害化。既定は不変。

**A11y**: キーボード完結は最初の画面の Issue から入れないと、後で入らない。

**研究 / 分析**: 統計・頻度・ヒストグラムは Should。値は文字列のまま、見方で。

**ログ / GIS / QA**: 追従・詳細ペイン・ダミーデータの生成は、それぞれ Should / Must / Could。

### 合意した優先度の考え方

- **Must**: 無いと SPECIFICATION の約束（勝手に変えない・巨大でも速い・壊れない）が成り立たないもの
- **Should**: 初版に入れたい。競合の多くが持つか、ヘビーユーザーの要望の上位
- **Could**: 後の版
- **Won't**: やらない（理由を書く）

### 残った論点（施主の判断が要る）

1. 手順（レシピ）の形式を独自にするか、OpenRefine / Frictionless などに寄せるか
2. SQL を入れるか（入れるなら、どの範囲の SQL か）
3. 業者別のプリセット（楽天・弥生・Shopify）を製品と一緒に配るか
4. xlsx の読み書き（SPECIFICATION 第 3 節では初版はやらない）
5. 和暦の変換を入れるか（元号の表を持つことになる）
6. 印刷と PDF の優先度（FR-017。ペルソナからの要望は弱い）
